================================================================================
  SPARK MAX Firmware 26.x  —  USB Write API Reference
  Reverse-engineered via SLCAN probe, March 2026
================================================================================


OVERVIEW
--------
Firmware 26.x uses SLCAN (Serial Line CAN) ASCII framing over USB CDC serial.
The device enumerates as VID=0x0483 / PID=0x5740. All communication is ASCII
text, not the raw 12-byte binary packets used by older firmware or
SPARK-MAX-Server.

On Linux, add the following udev rule to prevent ModemManager from claiming
the port for ~15 seconds on connect:

  ATTRS{idVendor}=="0483", ATTRS{idProduct}=="5740", ENV{ID_MM_DEVICE_IGNORE}="1"


────────────────────────────────────────────────────────────────────────────────
SLCAN FRAME FORMAT
────────────────────────────────────────────────────────────────────────────────

Every CAN frame is sent and received as an ASCII line:

  T{XXXXXXXX}{N}{DD...}\r\n

  T          = extended (29-bit) CAN frame marker
  XXXXXXXX   = 8 hex chars, 29-bit CAN ID, big-endian
  N          = DLC: number of data bytes (1 hex digit, 1–8)
  DD...      = 2*N hex chars of payload data
  \r\n       = CRLF terminator

Example:
  T02051C4A8 07 00 CD CC 4C 3D 03 00\r\n


────────────────────────────────────────────────────────────────────────────────
CAN ID BIT LAYOUT  (FRC standard, 29-bit extended frame)
────────────────────────────────────────────────────────────────────────────────

  bits [28:24]  Device Type   = 0x02  (motor controller)
  bits [23:16]  Manufacturer  = 0x05  (REV Robotics, changed from 0x15 in fw26)
  bits [15:10]  API Class     (6 bits)
  bits  [9:6]   API Index     (4 bits)
  bits  [5:0]   Device CAN ID (6 bits, 0–63)

Python helper:

  def make_can_id(api_class, api_index, device_id):
      return (
          (0x02 & 0x1F) << 24 |
          (0x05 & 0xFF) << 16 |
          (api_class  & 0x3F) << 10 |
          (api_index  & 0x0F) << 6  |
          (device_id  & 0x3F)
      )

NOTE: The manufacturer code changed from 0x15 (used by old firmware and
SPARK-MAX-Server) to 0x05 in firmware 26.x. Frames built with 0x15 are
silently ignored by fw26 devices.


────────────────────────────────────────────────────────────────────────────────
PARAMETER READ  (API Class=7, Index=1)
────────────────────────────────────────────────────────────────────────────────

Request payload (8 bytes):
  [param_id] [0x00] [0x00] [0x00] [0x00] [0x00] [0x00] [0x00]

Response payload (8 bytes, returned on the same API Class=7 channel):
  byte[0]   = param_id (echo)
  byte[1]   = 0xFF     (read response marker)
  bytes[2:6]= value, little-endian (interpret as float32 or uint32 per type tag)
  byte[6]   = type tag:  0x00=bool, 0x02=int, 0x03=float, 0x04=uint
  byte[7]   = 0x00      (reserved / no error)

Example — read kInputDeadband (param_id=7):
  Send:  07 00 00 00 00 00 00 00
  Recv:  07 FF CD CC 4C 3D 03 00
         ^  ^  [----float----] ^  ^
         |  |                  |  reserved
         |  read marker        type=float
         param_id echo
  float32(0xCD, 0xCC, 0x4C, 0x3D) = 0.05


────────────────────────────────────────────────────────────────────────────────
PARAMETER WRITE  (API Class=7, Index=0)
────────────────────────────────────────────────────────────────────────────────

CONFIRMED PAYLOAD FORMAT (fw26):
  byte[0]   = param_id
  byte[1]   = 0x00
  bytes[2:6]= value, little-endian (float32 or uint32 per type tag)
  byte[6]   = type tag  (MUST match the type tag the device returns on read)
  byte[7]   = 0x00

  ┌─────────┬──────┬──────────────────────┬──────────┬──────┐
  │ param_id│ 0x00 │  value (4 bytes LE)  │ type_tag │ 0x00 │
  └─────────┴──────┴──────────────────────┴──────────┴──────┘

Type tags:
  0x00 = bool   → pack as uint32 (0 or 1)
  0x02 = int    → pack as uint32 little-endian
  0x03 = float  → pack as float32 little-endian
  0x04 = uint   → pack as uint32 little-endian

CRITICAL: The type tag in the write payload must exactly match the type tag
the device reports in its read response for that parameter. Sending the wrong
type tag results in a kTimeout error (byte[7]=0x02 in the response) and the
value is not written.

ACK response (returned on API Class=7):
  byte[0]   = param_id (echo)
  byte[1]   = 0x00     (success — NOT 0xFF like read responses)
  bytes[2:6]= written value (echo)
  byte[6]   = type tag (echo)
  byte[7]   = 0x00     (success)

NAK / error response:
  byte[7]   = 0x02     (kTimeout — write rejected)

NOTE: The device will also echo the raw SLCAN frame back through the bridge.
Discard any response where the CAN ID and payload exactly match what was sent.
Only process frames where byte[1]=0x00 and byte[7]=0x00 as a confirmed ACK.

Example — write kInputDeadband (param_id=7) = 0.10:
  float32(0.10) = CD CC CC 3D
  Send:  07 00 CD CC CC 3D 03 00
  Recv:  07 00 CD CC CC 3D 03 00   ← ACK  (b1=0x00, b7=0x00)

ZERO-VALUE TYPE TAG QUIRK:
  When a float parameter's current value is exactly 0.0, the device may report
  its type tag as 0x00 (bool) instead of 0x03 (float). This appears to be a
  firmware bug where uninitialized/zero-value storage is misidentified.
  Always use the type tag from the official parameter table below when writing,
  not blindly from the read response, if the current value is 0.


────────────────────────────────────────────────────────────────────────────────
BURN TO FLASH  (API Class=6, Index=1)
────────────────────────────────────────────────────────────────────────────────

Written parameters are held in RAM only until the device is power-cycled.
To persist them, send a burn-flash command and wait 300ms:

  Payload: 00 00 00 00 00 00 00 00   (8 zero bytes)

Do not send any further commands for at least 300ms while flash is writing.
The device is unresponsive during this window.


────────────────────────────────────────────────────────────────────────────────
HEARTBEAT  (API Class=6, Index=0)
────────────────────────────────────────────────────────────────────────────────

The motor will not respond to setpoint commands without a heartbeat. Send
this frame every ≤100ms (80ms recommended) in a background thread:

  Payload: 00 00 00 00 00 00 00 00

No roboRIO is required when sending the heartbeat via USB.


────────────────────────────────────────────────────────────────────────────────
MOTOR CONTROL SETPOINTS
────────────────────────────────────────────────────────────────────────────────

All setpoint payloads are a 4-byte little-endian float32 followed by 4 zero bytes.
Heartbeat must be active or the motor will not move.

  Duty Cycle  API Class=0, Index=2   range: -1.0 to 1.0
  Velocity    API Class=0, Index=11  units: RPM
  Position    API Class=0, Index=10  units: rotations
  Voltage     API Class=0, Index=12  units: volts

PARAMETERS THAT PERSIST THROUGH FIRMWARE UPDATE
------------------------------------------------
  kCanID (0), kMotorType (2), kSensorType (4), kIdleMode (6), kDataPortConfig (127)

These survive a normal OTA firmware update. All others reset to defaults.


KNOWN GOTCHAS
-------------
  - kSensorType (ID 4) was REMOVED in firmware 25+. Do not attempt to write it;
    the device will reject it or behave unexpectedly.

  - The manufacturer code changed from 0x15 to 0x05 in fw26. Any tool built
    against SPARK-MAX-Server or old REVLib that hardcodes 0x15 will be invisible
    to fw26 devices.

  - ModemManager on Linux will claim the serial port for ~15s after connect.
    Add the udev rule described at the top of this file.

  - Only one process can own the serial port at a time. Close RHC2 before
    running custom scripts.

  - kCanID changes do not take effect until the device is power-cycled after
    flash burn. The device continues to respond on the old ID until then.

  - If previously on a roboRIO CAN bus, power-cycle the controller after
    disconnecting to clear any CAN lockout state.

  - Sending duty-cycle setpoints while kCurrentChop is set to its factory
    default (115A) can cause unexpected torque limiting at high currents.
    Set kCurrentChop=0 to disable if not needed.
